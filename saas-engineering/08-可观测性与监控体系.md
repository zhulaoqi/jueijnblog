# 可观测性与监控体系：系统运行的第一现场

> 没有监控的 SaaS 系统，就像没有仪表盘的飞机驾驶舱。你可以飞，但你不知道飞到哪里、燃油还剩多少、引擎是否正常。出了问题，只能靠感觉猜。
>
> 监控不是系统做好后"顺手补上"的锦上添花，而是所有工程决策的信息基础：弹性扩缩触发什么？降级决策怎么做？SLO 怎么计算？故障如何定位？**所有这些能力的背后，都是监控系统在提供数据。**
>
> 本文是整个系列的"基础设施篇"——把监控体系作为系统运行的第一现场来研究。

---

## 一、可观测性的三个支柱

| 支柱 | 本质 | 典型内容 | 适用场景 | 工具 |
|------|------|---------|---------|------|
| **📊 Metrics（指标）** | 量化的数字，反映系统状态 | QPS、延迟、错误率、CPU、内存、连接数、队列积压量 | 趋势分析、告警、SLO 计算 | Prometheus + Grafana |
| **📝 Logs（日志）** | 带上下文的事件记录 | 请求日志（入参、出参、耗时）、错误日志（异常栈）、业务操作日志 | 故障排查、根因分析、审计 | ELK Stack / Loki + Grafana |
| **🔍 Traces（链路追踪）** | 跨服务的请求调用路径 | 完整调用链（服务A→服务B→DB）、每段耗时、跨服务 Span 传播 | 性能瓶颈定位、跨服务故障定位 | Jaeger / SkyWalking / Tempo |

**三者是互补的，不是替代关系。** 实际排查故障时，形成完整闭环：

```
Metrics 发现问题（某接口错误率升高）
    ↓
Logs 定位上下文（找到错误发生时的请求详情）
    ↓
Traces 追踪根因（定位是哪个下游服务调用超时）
    ↓
回到 Metrics（查看那个下游服务的资源指标趋势）
```

## 二、监控是第一现场：它如何驱动所有工程决策

### 2.1 没有监控时的工程现状

```
用户报障才知道系统有问题（MTTD 极长）
靠猜测判断要不要扩容（浪费或不够用）
SLO 是什么？不知道当前达没达到
故障排查：凭经验 + 运气（MTTR 极长）
降级决策：感觉不对就降级（过度降级或降级太晚）
```

### 2.2 建立监控后，每个工程能力的信息来源

| 工程能力 | 依赖的监控数据 |
|---------|--------------|
| 弹性扩缩（KEDA 自动触发）| Prometheus 的 Kafka Consumer Lag 指标 |
| 降级决策（熔断器自动开启）| Prometheus 的错误率 / 延迟指标 |
| SLO 计算（Error Budget 消耗）| Prometheus 的成功率指标（成功请求 / 总请求）|
| Noisy Neighbor 识别 | per-tenant 的资源消耗 Metrics |
| 故障定位（精确到根因）| Trace + Log 联合排查 |
| 容量规划（下个月需要多少资源）| 历史 Metrics 趋势 + Log 访问模式 |

## 三、SaaS 监控的特殊要求：租户维度

SaaS 系统监控与单租户系统最大的区别：**所有指标都必须有 `tenant_id` 维度。**

### 3.1 为什么 tenant_id 是核心 Label

| 没有 tenant_id 维度 | 有 tenant_id 维度 |
|-------------------|-----------------|
| 告警：API 错误率升高，无法判断影响了哪些租户 | 精确定位受影响租户，只通知受影响的客户 |
| 无法发现 Noisy Neighbor | 发现：「租户 ACME 消耗了 40% CPU」|
| 无法计算 per-tenant SLO，无法做租户级别稳定性承诺 | per-tenant SLO 追踪，大客户享受更高 SLO 保障 |
| 客户投诉：「你们系统有问题」→ 我看不到你的请求数据 | 立即查到该租户的请求历史，秒级响应 |

### 3.2 关键指标的 tenant_id 埋点

```promql
# 每个租户的 API 请求量（Prometheus 格式）
http_requests_total{
    service="api-gateway",
    tenant_id="acme",
    endpoint="/api/orders",
    method="POST",
    status_code="200"
}

# 每个租户的 P99 延迟
histogram_quantile(0.99,
    rate(http_request_duration_seconds_bucket{tenant_id="acme"}[5m])
)

# 发现 Noisy Neighbor：按租户聚合 CPU 消耗占比
sum(rate(container_cpu_usage_seconds_total{namespace="saas-platform"}[5m]))
    by (tenant_id)
/
sum(rate(container_cpu_usage_seconds_total{namespace="saas-platform"}[5m]))
```

## 四、黄金指标：SaaS 系统必须监控的核心指标

### 4.1 Google SRE 四个黄金信号

| 信号 | 说明 | 监控重点 |
|------|------|---------|
| 🔴 **延迟（Latency）** | P50 / P95 / P99 响应时间 | 区分成功请求和失败请求的延迟（失败快不算好）|
| 🟠 **流量（Traffic）** | QPS / RPS | 理解系统当前承受的压力 |
| 🔵 **错误率（Errors）** | 5xx 错误 / 总请求 | 业务错误 ≠ HTTP 错误，需要都追踪 |
| 🟡 **饱和度（Saturation）** | CPU / 内存 / 连接数 / 磁盘使用率 | 预测系统什么时候会被撑满 |

### 4.2 SaaS 系统的分层监控指标

| 层次 | 关键指标 | 优先级说明 |
|------|---------|---------|
| **用户体验层**（最重要）| 核心接口成功率 (per-tenant)、核心接口 P99 延迟 (per-tenant)、支付成功率 | 直接反映用户感知，告警必须立即响应 |
| **应用层** | 服务 QPS / 错误率、JVM GC 时间 / 堆使用率、线程池队列深度、熔断器状态变化 | 中间层，辅助定位问题 |
| **数据层** | 数据库连接池使用率 (per-tenant)、慢查询数量 (>1s)、主从复制延迟、Redis 命中率、Kafka Consumer Lag (per-tenant) | 数据层是很多性能问题的根源 |
| **基础设施层** | Node CPU / 内存、Pod 重启次数、网络 I/O 带宽、磁盘使用率趋势 | 基础设施异常 ≠ 用户有问题，但是预警信号 |

**优先级原则**：用户体验层告警 = 用户一定有问题（立即响应）；基础设施层告警 ≠ 用户一定有问题（可分析）。

## 五、告警设计：从噪声中提取有效信号

### 5.1 告警噪声是比没有告警更严重的问题

```
每天收到 500 条告警
  → 工程师开始忽略告警
  → 真正的故障埋没在噪声里
  → 等用户报障才发现
  → 比没有告警还危险（有误报的安全感）
```

**好的告警应该满足：**
- 每个告警都需要人处理（不处理就是 Bug 或告警规则有问题）
- 告警及时性：故障发生后 5 分钟内触发
- 告警可操作性：收到告警知道去做什么，有 Runbook 链接
- 告警不重复：同一根因触发一条，不是一百条

### 5.2 基于 SLO 的告警：告警最正确的姿势

基于资源阈值的告警（"CPU > 80% 告警"）误报率高。**基于 SLO 和 Burn Rate 的告警，才是真正面向用户体验的告警。**

**Burn Rate 分级告警：**

| Burn Rate | 含义 | 通知方式 | 响应要求 |
|-----------|------|---------|---------|
| > 14x | 当天会耗尽月度 Error Budget | PagerDuty 立即电话 | **立即响应** |
| 5x - 14x | 本周会耗尽 Error Budget | Slack 告警 | 今天内处理 |
| 1x - 5x | 本月消耗略超预期 | 工单 | 本周评审 |
| < 1x | 正常，预算消耗比预期慢 | 无需告警 | — |

```promql
# Burn Rate 计算（Prometheus）
# 假设 SLO = 99.9%，Error Budget Rate = 0.1%

(
    sum(rate(http_requests_total{status=~"5.."}[1h]))
    /
    sum(rate(http_requests_total[1h]))
)
/
(1 - 0.999)   # Error Budget Rate = 0.001
```

### 5.3 告警的分级策略

| 告警级别 | 触发条件 | 通知方式 | 响应时间要求 |
|---------|---------|---------|------------|
| P0 - 紧急 | Burn Rate > 14x / 核心链路不可用 | 电话 + PagerDuty | 立即响应，5 分钟内处理 |
| P1 - 重要 | Burn Rate > 5x / 重要功能降级 | PagerDuty + 钉钉 | 30 分钟内响应 |
| P2 - 一般 | SLO 消耗超预期 / 性能下降 | 钉钉群 + 工单 | 当天内处理 |
| P3 - 信息 | 趋势异常 / 潜在风险 | 邮件 + Dashboard | 本周内评估 |

## 六、分布式追踪：故障定位的关键工具

### 6.1 为什么需要 Trace

在微服务 + SaaS 多租户架构中，一个用户请求可能跨越 5-10 个服务，日志无法还原完整路径：

```
用户 → API Gateway（traceId: abc123）
    → Auth Service（spanId: 001, 耗时 12ms）验证通过
    → Business Service（spanId: 002）
        → Redis Cache（spanId: 003, 耗时 2ms）Cache Miss
        → Database（spanId: 004, 耗时 850ms）← 慢查询！
    → 返回用户（总耗时 885ms）

Trace 清晰显示：瓶颈在 DB 查询（占总耗时 96%）
如果只有日志，需要在 5 个服务里分别搜索，无法关联
```

### 6.2 Trace 的关键实践

每个 Span 必须包含的信息：

| 字段 | 说明 |
|------|------|
| `trace_id` | 跨服务全局唯一 ID（**所有服务日志都要带这个**）|
| `span_id` | 单个服务内的操作 ID |
| `tenant_id` | SaaS 必须有，用于 per-tenant 分析 |
| `service_name` | 哪个服务产生的 span |
| `duration_ms` | 这个 span 的耗时 |
| `status` | 成功 / 失败 / 降级 |

**黄金规则**：`trace_id` 必须从请求入口一路传播到所有下游服务（通过 HTTP Header、MQ 消息头、DB 注释等），任何断点都会导致 Trace 断链，无法还原完整调用路径。

## 七、监控大盘：给不同角色看不同的视角

### 7.1 不同角色需要不同的监控视角

| 大盘类型 | 目标受众 | 核心内容 | 设计原则 |
|---------|---------|---------|---------|
| **业务大盘** | 管理层 / 产品 | 活跃租户数 / DAU、核心业务成功率、SLO 达标情况 | 不涉及技术细节，结论导向 |
| **服务健康大盘** | SRE / On-Call | 所有服务错误率 / 延迟、Error Budget 消耗进度、告警列表 | 需要立即关注的异常要突出显示 |
| **租户健康大盘** | 技术支持 | 指定租户的请求量 / 错误率、资源使用情况、历史事件 | 支撑客户投诉排查，查询要快 |
| **基础设施大盘** | 运维 / SRE | 集群资源使用率、Pod / Node 状态、存储容量趋势 | 趋势图 + 告警阈值线 |

### 7.2 监控大盘的设计原则

- **顶层是结论，底层是证据**：大盘首屏显示"系统是否健康（红/黄/绿）"，钻取后才看技术细节
- **关联跳转**：从告警点击直接跳转到相关的 Log 查询和 Trace 视图
- **时间对齐**：所有图表的时间轴要能同时调整，便于关联分析

## 八、监控体系的建设路径

**不要等到完美再开始，先有再好：**

| 阶段 | 目标 | 行动 |
|------|------|------|
| **第一阶段：有比没有好** | 能发现服务宕机 | 接入基础 Metrics（请求量、错误率、延迟）；设置核心告警（服务宕机、错误率突增）；集中日志（至少能搜索）|
| **第二阶段：面向 SLO** | 能量化稳定性 | 定义 SLO，计算 Error Budget；基于 Burn Rate 的告警替代基于阈值的告警；per-tenant 指标（加上 tenant_id label）|
| **第三阶段：面向可观测性** | 能快速定位根因 | 接入分布式追踪，Trace + Log 联动；trace_id 全链路传播；建设面向不同角色的业务大盘 |
| **第四阶段：主动式治理** | 能预测和预防问题 | 异常检测（ML 基线告警，减少噪声）；容量预测（基于趋势的容量规划）；混沌工程集成 |

**关键建议**：第一阶段的监控（5 个关键指标 + 3 个核心告警）就能避免 80% 的"用户报障才知道系统有问题"的情况。**先有再好，不要追求完美而迟迟不建设。**

## 研究小结

**认知一：监控不是"做完系统后补的工具"，而是系统的一部分**

如果监控是事后补的，那么 SLO 无法定量，降级无法自动触发，故障排查靠猜。从第一个服务上线开始，就应该有基础监控。

**认知二：告警质量比告警数量更重要**

收到 500 条告警的工程师，比收到 0 条告警的工程师更危险——他们会忽略所有告警。每一条告警都应该是"有人必须处理的信号"。

**认知三：tenant_id 是 SaaS 监控的核心维度**

所有指标都必须有 tenant_id。这不只是技术要求，也是商业能力：能给每个客户出具详细的服务质量报告，是企业级 SaaS 的基本能力。

---

**核心思考框架**

建立监控体系时，需要能回答这五个问题：

1. 系统出现问题，你是先于用户知道，还是用户报障后才知道？（检测延迟）
2. 收到告警，你知道去哪里找信息定位根因吗？（信息可获取性）
3. 你能告诉任意一个客户，过去一个月他们的服务可用性是多少吗？（per-tenant 可观测性）
4. 弹性扩缩和降级决策的触发条件，是基于监控指标自动化的，还是靠人工判断？（决策自动化）
5. 最近一次告警，告警到恢复的全链路，信息是否完整？（事后可复盘性）
