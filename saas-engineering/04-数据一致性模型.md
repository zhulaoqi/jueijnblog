# 数据一致性模型：分布式系统中最重要的业务决策

> "我们需要强一致性"——这句话在设计评审中经常被说出来，但很少有人认真考虑它的代价。强一致性要求多节点间协调，协调带来延迟，延迟降低可用性，可用性下降影响 SLO，SLO 违约产生商业损失。
>
> 一致性不是非黑即白的技术选项，而是一个**在正确性、延迟、可用性、成本之间做权衡的业务决策**。架构师的职责是把这个权衡讲清楚，让业务方做决定，而不是单方面选择"技术上正确"的方案。

---

## 一、为什么分布式系统必须面对一致性问题

单机系统没有一致性问题——所有操作串行执行，读到的永远是最新写入。

SaaS 系统有三个无法回避的结构性特征，使一致性问题必然存在：

| 原因 | 机制 | 导致的问题 |
|------|------|---------|
| **多副本存储** | 高可用需要数据冗余，副本间同步有延迟 | 读到旧数据（Stale Read）|
| **多区域部署** | 用户就近读写，跨区域同步有延迟 | 读到旧数据 + 写写冲突 |
| **并发写入** | 多用户/多服务同时修改同一数据，需要并发控制 | 写写冲突 + 数据丢失（Lost Update）|

## 二、CAP 与 PACELC：理论到工程的翻译

### 2.1 CAP 定理的工程含义

CAP 定理告诉我们：分布式系统在网络分区时，只能选择一致性（C）或可用性（A）。

**常见误解 vs 工程真相：**

```
❌ 常见误解：CAP 是三选二

✅ 工程真相：
  1. P（分区容错）不是可以放弃的选项
     → 网络分区在分布式系统中必然发生（网络抖动、节点重启、机房隔离）

  2. 真正的选择是：当网络分区发生时
     → 选 C：拒绝服务，等分区恢复（CP 系统）
     → 选 A：继续服务，接受数据不一致（AP 系统）

CP 系统示例：ZooKeeper、etcd
  → 选择在分区时拒绝写入，保证读到的一定是最新数据

AP 系统示例：Cassandra、DynamoDB 默认配置
  → 选择在分区时继续服务，允许不同节点暂时有不同的数据
```

### 2.2 PACELC：正常运行时的取舍

CAP 描述的是"分区时"的极端情况。但**即使没有分区，正常运行时也存在延迟（L）和一致性（C）的权衡：**

| 复制方式 | 延迟 | 一致性 | 适用场景 |
|---------|------|--------|---------|
| **同步复制** | 高（写操作等待所有副本确认）| 强 | 金融交易、权限变更（对延迟不敏感，对正确性极敏感）|
| **异步复制** | 低（写操作确认主节点后立即返回）| 弱（副本有数据延迟）| 统计数据、搜索索引（对延迟敏感，可接受短暂不一致）|

**这才是 SaaS 日常工程决策的核心权衡。** 不是"分区时怎么办"，而是"为了降低正常请求的延迟，愿意接受多长时间的数据不一致"。

## 三、一致性谱系：为每个业务场景选择合适的模型

```
强一致性（Strong）
  → 写操作等待所有副本确认，所有节点同时看到最新值
  → 代价：高延迟，可用性低

        ↓ 放宽

因果一致性（Causal）
  → 有因果关系的操作在所有节点保持顺序，并发操作顺序可以不同
  → 代价：需要向量时钟，中等复杂度

        ↓ 放宽

会话一致性（Read Your Writes）
  → 同一 Session 内读操作一定看到自己的写入，不同 Session 间可以不一致
  → 代价：需要路由写入节点的读请求

        ↓ 放宽

最终一致性（Eventual）
  → 停止写入后，经过一段时间，所有副本收敛到相同值
  → 代价：读到旧数据的时间窗口
```

### 3.1 业务场景与一致性模型的对应

**这是架构师需要和业务方一起做的决定，不能技术团队单方面定。**

| 业务操作 | 推荐一致性 | 为什么 | 错误选择的后果 |
|---------|-----------|--------|--------------|
| 账户余额扣减 | 强一致性 | 双重扣款是严重业务错误 | 用户被多扣款，法律纠纷 |
| 权限撤销立即生效 | 接近强一致性 | 安全漏洞 | 撤销权限后用户仍可访问 |
| 用户保存文档后刷新 | 会话一致性 | 用户必须立即看到自己的操作结果 | 用户误以为保存失败 |
| 评论/回复显示顺序 | 因果一致性 | 回复必须出现在原帖之后 | 界面显示"回复"先于"原帖"，混乱 |
| 报表统计数字 | 最终一致性 | 1-5 分钟延迟业务完全可接受 | 无实际影响，但实现强一致代价极高 |
| 搜索结果更新 | 最终一致性 | 新内容在搜索中出现延迟是行业标准 | 无实际影响，实现强一致成本巨大 |
| 跨区域副本读取 | 最终一致性（带标记）| 跨区域延迟不可消除 | 追求强一致会导致写延迟极高 |

## 四、最终一致性的工程实现：不是"不需要工程"

最终一致性并不意味着"随便，总会一致的"。要做到**正确的最终一致性**，需要解决一系列工程问题。

### 4.1 Outbox Pattern：保证变更不丢失

**核心问题**：如何保证"业务数据写入"和"变更事件发布"的原子性？

**错误做法（有数据丢失风险）：**
```
步骤 1：写入数据库（成功）
步骤 2：发布 MQ 消息（失败！网络超时）
→ 下游永远不知道这次变更，数据永久不一致
```

**Outbox 正确做法：**
```
同一个数据库事务中：
  步骤 1：写入业务数据
  步骤 2：写入 outbox_events 表（status=PENDING，同一 DB，同一事务）
  COMMIT（原子性保证：要么都成功，要么都失败）

Message Relay 进程（独立）：
  每 5 秒扫描 status=PENDING 的事件
  → 发布到 MQ
  → MQ 确认后更新 status=SENT
  → 发布失败：保持 PENDING，下次继续重试（事件不丢失）

下游消费者：
  幂等消费（可能收到多次，结果相同）
```

**为什么这样做有效**：业务数据和 outbox 事件在同一事务里，要么都写成功，要么都失败。Relay 进程独立重试，不会因为网络抖动导致事件丢失。

### 4.2 Saga 模式：跨服务的数据一致性

当一个业务操作需要跨多个服务时，传统数据库事务无法跨服务使用。Saga 通过"补偿事务"实现跨服务一致性：

**Saga 示例（下单流程）：**

```
Orchestrator 执行正向步骤：
  ① createOrder()        → ✅ 成功
  ② reserveItem()        → ✅ 成功
  ③ charge()             → ❌ 失败（余额不足）

触发补偿事务（逆向执行，每步都是幂等的）：
  ④ releaseItem()        → 补偿步骤 ②
  ⑤ cancelOrder()        → 补偿步骤 ①

最终状态：所有数据保持一致（通过补偿实现，不是传统回滚）
```

**Saga 的关键设计要求**：
- 每个步骤的补偿操作必须是**幂等的**（可能被重复调用）
- Orchestrator 的状态必须**持久化**（重启后能继续执行）
- 补偿操作也可能失败，需要**重试机制**

## 五、冲突解决策略：当并发写入不可避免时

### 5.1 四种策略的选择框架

```
写冲突发生时，什么数据语义对业务是正确的？
    ↓
【问】是否允许静默丢失某个写操作？
    → 允许丢失（最新的才重要）
        → Last Writer Wins（LWW）
           时间戳更大的覆盖旧值
           适用：用户配置、状态字段
           缺点：时钟不精确时可能选错

    → 不允许丢失任何写操作
        → 【问】业务能否接受用户手动解决冲突？
            → 能
                → Multi-Version（保留所有冲突版本，展示给用户选择）
                   适用：文档内容、重要配置
                   缺点：需要用户干预

            → 不能，需要自动合并
                → 【问】数据能否用 CRDT 建模？
                    → 能（计数器/集合/有序文本）
                        → CRDT 数据结构
                           任意顺序合并，结果确定
                           适用：协作文档、计数器、标签
                           缺点：只适合特定数据类型

                    → 无法用 CRDT 建模
                        → 单主写入
                           所有写入路由到主区域
                           适用：强一致性场景
                           缺点：写延迟高，但合理
```

### 5.2 监控冲突情况

无论选择哪种冲突解决策略，都需要监控冲突发生的频率和解决结果：

```promql
# 冲突相关监控指标
conflict_detected_total{strategy="lww", winner="local"}
conflict_detected_total{strategy="lww", winner="remote"}
conflict_pending_user_resolution_count   # 等待用户解决的冲突数
conflict_resolution_latency_seconds      # 用户解决冲突的时间
```

高冲突率是数据架构设计有问题的信号，而不是"正常现象"。

## 六、架构师的判断：如何与业务对齐一致性决策

**这是最难教但最重要的能力。**

正确的对话模板：

```
工程师（❌ 错误做法）：
"这个数据我们用最终一致性，可以接受 30 秒延迟。"
（没有和业务对齐，单方面决定）

工程师（✅ 正确做法）：
"用户更新了个人资料后，搜索结果里的展示信息需要多快更新？
 - 立即更新（< 1 秒）：我们需要同步更新搜索索引，成本高很多
 - 1 分钟内：异步更新，成本低，只是用户搜索到自己时可能看到旧信息
 - 5 分钟内：跟搜索引擎的普遍行为一致，用户一般不会注意到
 建议选 1 分钟，但最终由你们决定这个延迟是否可接受。"
```

**原则：工程师提供选项和代价，业务方做决定。这样的一致性决策才有真实的业务背书，出了问题也能共同承担。**

## 研究小结

一致性设计的三个层次：

1. **识别**：哪些操作需要强一致性，哪些可以接受最终一致性
2. **实现**：选择合适的技术（同步复制、Outbox、Saga、CRDT）
3. **监控**：数据延迟、冲突率、补偿事务失败率——没有这些监控，你不知道一致性保障是否在工作

**最终一致性不是"便宜货"，是在业务允许的前提下，用更低的成本获得更高的可用性和更低的延迟。选择它需要理由，不选它也需要理由。**
