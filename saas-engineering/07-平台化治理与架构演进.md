# 平台化治理与架构演进：DDD、技术债与可持续的工程节奏

> 架构不是一次性决策，是在业务增长中持续演进的过程。今天"正确"的架构，可能一年后因为规模、团队、业务的变化而成为瓶颈。
>
> 架构治理最难的不是选技术，而是**在正确的时机做正确的事**——既不超前（增加不必要的复杂度），也不滞后（债务积累到无法偿还）。本文研究 SaaS 系统长期可持续演进的核心命题。

---

## 一、复杂度是如何悄悄积累的

### 1.1 复杂度积累的三条路径

**路径一：功能堆积**
```
为特殊客户加 if-else
  → 积累 50+ 个 if-else
  → 改一处影响多处，没人敢动这段代码
```

**路径二：团队扩张**
```
3 人团队，口头沟通架构
  → 30 人团队，各自重复建轮子
  → 业务概念定义混乱，接口不一致
```

**路径三：技术债积压**
```
早期走捷径，快速上线
  → 债务没有记录，没有计划偿还
  → 每次需求都要绕过历史债务，越来越慢
```

### 1.2 复杂度失控的症状信号

| 症状 | 描述 | 潜在根因 |
|------|------|---------|
| 需求估时越来越不准 | 本来 3 天的功能，实际要 3 周 | 代码耦合，改一处动多处 |
| Bug 修复引入新 Bug | 每次发布后新增 1-2 个回归问题 | 没有清晰边界的模块化 |
| 新人上手时间超过 1 个月 | 业务逻辑散落各处，理解成本极高 | 代码与业务概念脱节 |
| 发布窗口越来越窄 | 从每天发布变成每周发布 | 变更影响面不可知，风险厌恶 |

当这些信号出现时，不是个人能力问题，而是架构需要治理的信号。

## 二、DDD：让代码与业务同步演进

### 2.1 DDD 解决的核心问题

**没有 DDD 的情况：**
```
业务团队用：「订单」「用户」「会员」
技术团队用：t_order、user_info、member_level
          ↕ 翻译频繁出错，理解成本极高
```

**有 DDD 的情况：**
```
通用语言（Ubiquitous Language）：代码里的类名 = 业务用的词汇
  Order / Customer / Subscription / TenantId

业务团队 ──使用同一套词汇──→ 通用语言 ←──代码直接体现──── 技术团队
```

**DDD 最大的价值不是技术工具，而是消除业务与技术之间的语言鸿沟。** 当业务说"暂停订阅"，代码里就应该有 `subscription.suspend()` 方法，而不是 `UPDATE tb_subscription SET status=2 WHERE id=?`。

### 2.2 战略设计：划定业务边界

SaaS 平台的限界上下文（Bounded Context）划分：

```
┌─────────────────────────────────────────────────────┐
│                   SaaS 平台                          │
│                                                      │
│  ┌────────────┐    ┌────────────┐    ┌────────────┐  │
│  │ 租户管理    │───→│ 订阅计费    │    │ 身份与访问  │  │
│  │ 上下文      │    │ 上下文      │    │ 上下文      │  │
│  │            │    │            │    │            │  │
│  │ 租户注册    │    │ 订阅计划    │    │ 用户认证    │  │
│  │ 配置管理    │    │ 发票生成    │    │ 权限控制    │  │
│  │ SSO 集成   │    │ 用量计量    │    │ RBAC       │  │
│  └─────┬──────┘    └─────┬──────┘    └─────┬──────┘  │
│        │                 │                 │          │
│        ↓ 租户变更事件     ↓ 支付成功事件     ↓ 权限验证  │
│  ┌──────────────────────────────────────────────────┐ │
│  │              核心业务上下文（因产品而异）            │ │
│  └──────────────────────────────────────────────────┘ │
│        ↓ 业务事件                                      │
│  ┌────────────┐                                        │
│  │ 通知上下文  │ 邮件/短信/Push、通知模板、发送记录       │
│  └────────────┘                                        │
└─────────────────────────────────────────────────────┘
```

**为什么要划定边界**："用户"在租户管理上下文是"管理员"，在核心业务上下文是"业务用户"，在计费上下文是"账单联系人"——同一个词，不同含义。边界内团队独立演进，跨边界只通过事件和接口通信。

### 2.3 聚合设计：用代码表达业务规则

```java
// 聚合根：Subscription
// 状态变更只通过方法，不允许外部直接 setStatus()
// 每次状态变更触发领域事件

public class Subscription {
    private SubscriptionId id;
    private TenantId tenantId;
    private Plan plan;
    private Status status;       // ACTIVE / SUSPENDED / CANCELLED
    private BillingCycle billingCycle;

    // 业务规则封装在聚合内部
    public SubscriptionSuspended suspend() {
        validateTransition(Status.SUSPENDED);  // 验证前提条件
        this.status = Status.SUSPENDED;
        return new SubscriptionSuspended(this.id, Instant.now());  // 触发领域事件
    }

    public SubscriptionRenewed renew() { ... }
    public SubscriptionCancelled cancel() { ... }

    private void validateTransition(Status newStatus) {
        // 暂停时需要验证什么前提条件（业务规则）
        // 这些规则在代码里，不会散落在服务层或控制器层
    }
}
```

**关键设计原则**：外部调用 `subscription.suspend()` 而不是 `setStatus(SUSPENDED)`。业务规则（暂停时需要验证什么前提条件）就在聚合内部，不会散落在服务层。

## 三、技术债：量化才能治理

### 3.1 技术债的四种类型与优先级

| 优先级 | 类型 | 典型例子 | 处理策略 |
|--------|------|---------|---------|
| 🔴 **立即处理** | 危害高 + 修复代价低 | EOL 组件安全漏洞、核心业务逻辑无测试覆盖 | 当前 Sprint 内处理 |
| 🟡 **计划处理** | 危害高 + 修复代价高 | 单体架构无法支撑当前规模、数据库无法水平分片 | 纳入季度专项 Sprint |
| 🟢 **纳入迭代** | 危害低 + 修复代价低 | 重复代码、过时注释、日志格式不统一 | 每 Sprint 消耗 15% 容量 |
| ⚪ **评估后决定** | 危害低 + 修复代价高 | API 版本升级、框架大版本迁移 | 季度评审时决定是否处理 |

### 3.2 技术债治理节奏

| 周期 | 行动 |
|------|------|
| **每个 Sprint（迭代内）** | 新引入债务记录到 Backlog；消耗 15% 容量偿还技术债 |
| **月度** | 评审债务列表排优先级；处理 1-2 个高优债务 |
| **季度** | 技术债专项 Sprint（整个 Sprint 专注还债）；架构评审 |
| **年度** | 技术战略规划；技术雷达评审 |

**最重要的原则**：技术债治理必须获得管理层支持，纳入正式规划，否则工程师只能在业余时间"偷偷还债"，效果很差且容易引发团队矛盾。

### 3.3 如何量化技术债的影响

| 可量化指标 | 说明 |
|-----------|------|
| 需求交付速度（Story Points/Sprint 趋势）| 趋势下降 = 技术债在拖慢交付 |
| Bug 密度（每 100 行代码的 Bug 数）| 上升 = 代码质量在恶化 |
| MTTR 趋势（修复同类故障是否越来越快）| 不快 = 知识没有沉淀，债务没有偿还 |
| Postmortem 中由技术债引起的故障比例 | 高 = 技术债直接影响稳定性 |
| 新人上手时间（从入职到第一个独立 PR）| 越来越长 = 系统可理解性在下降 |

**量化数据 → 管理层支持**："上个季度 30% 的故障由技术债导致"比"代码很乱"更有说服力。

## 四、架构演进：在正确时机做正确的事

### 4.1 架构演进的触发信号

```
收到架构演进信号
    ↓
信号类型？
    → 性能瓶颈（优化已无明显收益）
        → 分析瓶颈层次
        → 先加读副本，再分库分表（按代价从低到高尝试）

    → 可用性风险（单点故障影响全局）
        → 解耦高危依赖
        → 引入熔断 + 降级，避免单点扩散

    → 开发效率下降（改功能要动太多文件）
        → 模块化 → 微服务
        → 渐进式拆分，不要一次性大迁移

    → 团队扩张（超过 15 人协作摩擦增大）
        → 康威定律：按业务域拆分团队
        → 服务边界对应团队边界

    → 合规新要求（现有架构无法满足）
        → 专项演进，最小侵入式改造
        → 不借机重构无关部分
```

**反面信号（不应该触发架构演进）**：
- "业界都在用微服务" → 跟风，不是解决实际问题
- "这段代码写得不够优雅" → 代码质量，不是架构问题
- "将来可能会有 10x 流量" → 未来的问题，用现在的代价解决

### 4.2 渐进式拆分：从单体到微服务的正确姿势

**阶段一：模块化单体**
```
① 识别边界（DDD 限界上下文）
② 建立包级别隔离（禁止跨包直接访问 DB）
③ 模块间接口化（类似服务调用的方式）
→ 目标：单体内部有清晰的服务边界
```

**阶段二：识别拆分候选**
```
优先拆分：
  ✓ 变更最频繁的模块（拆分收益最大）
  ✓ 需要独立扩展的模块（弹性需求不同）
  ✓ 技术栈需要差异化的模块（如 AI 服务用 Python）
```

**阶段三：渐进拆分（Strangler Fig 模式）**
```
① 新功能先在新服务开发
② 存量功能逐步迁移（路由层将旧请求转发到新服务）
③ 验证稳定后下线旧模块

⚠️ 不要做：一次性将整个单体拆成微服务（代价极高，风险极大）
```

### 4.3 Shopify 的反直觉选择：保持模块化单体

Shopify 的核心业务至今是一个 Ruby on Rails 单体应用（2026 年仍在运行），支撑着每分钟数亿次请求。他们没有走微服务路线，而是：
- **内部模块化**：严格的包边界，模块间接口调用
- **基础设施 Pod 化**：数据库、缓存等有状态资源按 Pod 隔离
- **Kubernetes 弹性**：无状态应用层水平扩缩

**启示**：微服务解决的是组织规模问题（多团队独立部署），不是性能问题。如果你的问题是性能，加 Pod 更直接；如果问题是组织协作效率，才考虑服务化。

## 五、SaaS 平台化的演进路径

| 阶段 | 特征 | 工程重点 | 典型触发条件 |
|------|------|---------|------------|
| **阶段一：多租户 SaaS** | 同一套功能，多客户使用 | 租户隔离 + 弹性扩缩 | 起点 |
| **阶段二：可配置 SaaS** | 客户通过配置定制行为（无需代码修改）| 工作流引擎 + 规则引擎 + 字段扩展 | 客户要求定制化时 |
| **阶段三：平台化 SaaS** | 开放 API + 生态，第三方在平台上构建产品（Shopify App Store / Salesforce AppExchange）| Developer Experience + 沙箱 + Webhook | 有足够规模形成生态时 |

**每个阶段演进的核心判断**：不要超前于业务需求。阶段一的公司建设阶段三的能力，是过度工程的典型。

## 研究小结

架构治理的三个核心认知：

**架构是约束的产物，不是自由创作**
脱离团队规模、业务规模、时间约束谈"最佳架构"没有意义。

**技术债是可管理的负债，不是需要消灭的敌人**
有意识承担 + 有计划偿还 = 成熟的工程节奏。

**演进节奏跟上业务，但不超前**
超前 → 不必要的复杂度；滞后 → 成为业务瓶颈。

**架构师的最高价值**：不是给出技术上最优的方案，而是在当前约束下找到最合适的方案，并设计好演进到下一阶段的路径。
